# 📊 Talk to Your Data: Natural Language to SQL Assistant

## Overview & Motivation

This project is an interactive web application that allows users to query a relational database using plain English. The AI agent translates natural language questions into highly optimized SQL queries, executes them against the backend database, and returns the results in a clean, user-friendly data table.

While the initial inspiration for this project came from an AI agent tutorial by Ankit Bansal, I completely re-engineered the architecture to align with enterprise Microsoft environments. Drawing on extensive experience with Microsoft database ecosystems, I shifted the backend from PostgreSQL to MS SQL Server, integrated Google's Gemini API, and deployed a fully cloud-native solution.

## Tech Stack & Architecture

* **Frontend:** Python, Streamlit, Pandas
* **AI Model:** Google Gemini 3.5 Flash (`google-genai` SDK, Pydantic for structured JSON)
* **Database:** Microsoft SQL Server (Local `SQLEXPRESS`), Azure SQL Database
* **Database Connectivity:** `pyodbc`
* **Deployment & Hosting:** GitHub, Streamlit Community Cloud

## Engineering Journey & Key Customizations

### 1. Adapting to the Microsoft Ecosystem (T-SQL vs. Standard SQL)

Standard SQL generated by generic AI models often fails or underperforms in SQL Server Management Studio (SSMS). I engineered the system to exclusively generate **T-SQL**. By refining the prompts and context provided to the Gemini API, the agent now correctly utilizes SQL Server-specific syntax (e.g., using `TOP` instead of `LIMIT`, and referencing the `dbo` schema instead of `public`).

### 2. UI/UX Refinement in Streamlit

To create a polished, production-ready interface for end-users, I customized the Streamlit appearance significantly:

* **Theme Configuration:** Implemented a persistent dark mode via a hidden `.streamlit/config.toml` file to reduce eye strain and provide a modern look.
* **Visual Identity:** Replaced default headers with analytical emojis (📊) and customized the page title to reflect the product's identity.
* **Data Presentation:** Utilized pandas dataframes within Streamlit to cleanly render the returned data while keeping the complex backend SQL logic completely invisible to the user.

## Cloud Deployment & Overcoming Roadblocks

The most significant technical hurdle was migrating the application from a local development environment to a public cloud accessible to clients via a simple URL.

### Resolving the Local Database Barrier

Initially, the application connected to a local SQL Server instance (`SQLEXPRESS`) using Windows Authentication (`Trusted_Connection=yes`). When deploying to Streamlit Cloud (which operates on Linux servers over the open internet), this local connection naturally failed.

To solve this, I executed a complete database migration to the cloud:

1. **Azure SQL Provisioning:** Created a secure, serverless Azure SQL Database leveraging the free tier to maintain cost-efficiency while gaining enterprise-grade cloud hosting.
2. **SSMS Migration:** Used the SQL Server Management Studio Deployment Wizard to extract the schema and data from the local `namastesql` database and publish it directly to the newly provisioned `namastesql_cloud` database on Azure.
3. **Overcoming Azure Firewall Restrictions:** Streamlit Cloud was initially blocked by Azure's default security rules. I analyzed the connection errors, identified the Streamlit client IP, and successfully configured Azure Networking to whitelist the required IP addresses, establishing a secure bridge between the two cloud platforms.

### Refactoring Database Connectivity (`sqldb.py`)

To support the new cloud infrastructure, I rewrote the database connection logic:

* Transitioned from Windows Authentication to standard SQL Authentication (`UID` and `PWD`).
* Enforced mandatory encryption (`Encrypt=yes`) for data in transit across the internet.
* Handled connection pooling and cursor closure elegantly using Python's `with` context managers.

## Security & Best Practices

Security was prioritized throughout the deployment phase:

* **Credential Isolation:** All sensitive credentials, API keys, and database server names were isolated in a `.env` file during local development.
* **Repository Hygiene:** The `.env` file was strictly excluded from version control, ensuring no sensitive data was ever pushed to GitHub.
* **Cloud Secrets Management:** For production deployment, environment variables were securely injected into the runtime using the Streamlit Community Cloud Secrets management dashboard.
